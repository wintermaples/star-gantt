# Plugin: i18n (`stargantt.i18n`)

Package: `@stargantt/plugin-i18n` — Layer 8.
Status: normative.

## Purpose

A multilingual label dictionary: a registry of per-locale translation tables with a configurable fallback chain, published as a service so hosts and plugins can resolve user-visible strings in the chart's language. Its primary use is building the `messages` config objects of the other official plugins from one bundled dictionary (`catalog()`, §1.4). The locale-orthogonality principle: the catalog supplies the *words*; `Intl` formatting (driven by the chart-wide `locale`) supplies the *formats* — the two are independent axes. The plugin renders nothing, contributes to no extension point, and registers no command. With no config the dictionary is empty and every lookup misses, so the default composition renders byte-identically with or without the plugin.

## 1. Service — `stargantt.i18n` → `I18nService`

```ts
// packages/plugins/i18n/src/index.ts (types in src/types.ts)
import type { Plugin, Store } from "@stargantt/core";

/** One locale's translation table: flat dot-separated keys to translated strings. */
export type TranslationEntries = Readonly<Record<string, string>>;

/** The observable dictionary state. */
export interface I18nState {
  /** The active locale (BCP-47). */
  readonly locale: string;
  /** The configured fallback chain, in order. */
  readonly fallbacks: readonly string[];
  /** The computed lookup order (lowercased, deduplicated, "en"-terminated). */
  readonly resolutionOrder: readonly string[];
  /** The registered locale tags, first-seen order, most-recent display casing. */
  readonly locales: readonly string[];
}

export interface I18nService {
  /** Set on every observable dictionary change (§1.3). */
  readonly state: Store<Readonly<I18nState>>;
  setLocale(locale: string): void;
  setFallbacks(chain: readonly string[]): void;
  add(locale: string, entries: TranslationEntries): void;
  remove(locale: string): void;
  t(key: string): string | undefined;
  has(key: string, locale?: string): boolean;
  catalog<T extends object>(prefix: string, defaults: T): T;
}

export interface I18nConfig {
  /** Active locale (BCP-47). Default: the chart's `PluginContext.locale`. */
  locale?: string;
  /** Fallback locales consulted, in order, after the active locale. Default `["en"]`. */
  fallbacks?: readonly string[];
  /** Initial dictionaries, keyed by locale tag. Default: none. */
  translations?: Readonly<Record<string, TranslationEntries>>;
}

export declare function i18n(config?: I18nConfig): Plugin<void>;

/** Hostless dictionary — same lookup semantics, usable before `Gantt.create()` (§1.5). */
export declare function createDictionary(config?: I18nConfig): I18nService;
```

Member count: 8 (the `state` store + 7 methods). The four state readers — `locale`, `fallbacks`, `resolutionOrder`, `locales` — are members of the `state` value, not methods; dictionary changes are observed via `state.subscribe()`.

### 1.1 The dictionary

Translation keys are flat, host-chosen strings; the recommended shape is `"<pluginCamelName>.<messageKey>"` (`"treeGrid.name"`, `"portfolio.panelTitle"`), which is what `catalog()` assumes. Values are plain strings only — function members of a `messages` config (builders) cannot be expressed in a dictionary and are out of the plugin's scope. The empty string is a usable value, stored and returned verbatim.

`add(locale, entries)` merges per-key into the named locale's table (last write wins); `remove(locale)` drops a whole locale table. `locales` lists the registered tags in first-seen order, each rendered as most recently supplied: a re-registration under a different casing merges into the same table and updates the display tag (the last registration contributing at least one entry wins; a contributing-nothing merge leaves the tag unchanged). Unusable arguments are silently ignored: a non-string or empty `locale`, a non-object `entries`, and any entry whose key or value is not a string (per-entry drop, not per-call).

### 1.2 Locale matching and the fallback chain

Locale tags match case-insensitively (`"ja-JP"` ≡ `"ja-jp"`). The resolution order of a lookup is, deduplicated, first occurrence winning: (1) the active locale, then its progressively shortened prefixes obtained by dropping the last `-` subtag (`"ja-JP-u-ca"` → `"ja-JP"` → `"ja"`); (2) each configured fallback, in order, each likewise followed by its shortened prefixes; (3) `"en"`, always appended as the terminal fallback if not already present. `t(key)` scans this order and returns the first table holding `key`, else `undefined` — the caller keeps its own default, which is what `resolveCatalog`-style merging expects; `t` never returns the key itself as text. `has(key, locale?)` answers for one specific locale table exactly (no chain) when `locale` is given, else whether `t(key)` would hit.

The active locale defaults to `PluginContext.locale`; a usable `config.locale` overrides it — deliberately, since the chart-wide locale drives `Intl` formatting while the dictionary may be maintained under a coarser tag. `setLocale` / `setFallbacks` change the chain at runtime; unusable arguments (non-string or empty locale, non-array chain) are ignored without a store set. A fallback array with unusable entries keeps the usable entries; an empty fallback array is honored (chain = active locale + terminal `"en"`).

### 1.3 The `state` store

Every observable dictionary change — an effective `setLocale`, an effective `setFallbacks`, and every `add` / `remove` that changes stored content — publishes one fresh `I18nState` snapshot. Stores perform no equality gating, so a translations-only change (an `add` merging entries into an already-registered locale) still notifies even though no `I18nState` field differs — consumers that cache resolved strings re-resolve on any notification. Ignored (unusable) calls and `remove()` of an unknown locale set nothing. A subscriber that needs to know what changed diffs `(next, prev)` (a translations-only change is the diff-less case). Reading `t()` / `catalog()` from inside a subscriber is safe; calling a mutator from inside a subscriber re-enters `set()` on the dispatching store and throws (architecture.md ch. 1.1 rule 2).

### 1.4 `catalog(prefix, defaults)`

Builds a message-catalog object for another plugin's `messages` config field: `catalog("treeGrid", treeGridDefaults)` returns `{ ...defaults }` where every member whose default value is a string and for which `t(prefix + "." + member)` hits is replaced by the translation. Members whose default is not a string (builders) are never overridden. An unusable `prefix` (non-string) or `defaults` (non-object) returns `defaults` unchanged (same reference); otherwise the result is a fresh object and `defaults` is never mutated.

### 1.5 `createDictionary()` — the hostless form

Sibling factories snapshot their config before `Gantt.create()` runs, so the service — which exists only after creation — comes too late to feed them. `createDictionary(config)` is the same implementation without a host: it returns an `I18nService` whose `locale` default is `"en"` (no context). Its `state` store is fully functional (`createStore` is context-free); subscriptions made outside any plugin context follow the architecture ch. 1.1 rule-3 fault handling (`console.error`, no bus). The intended pattern:

```ts
const dict = createDictionary({ locale: "ja", translations: { ja: { "treeGrid.name": "名前" } } });
const gantt = Gantt.create({
  locale: "ja-JP",
  plugins: [ ..., treeGrid({ messages: dict.catalog("treeGrid", treeGridDefaultMessages) }), i18n({ ... }) ],
});
```

Whether a sibling exports its defaults object is that sibling's concern; `catalog()` also works with a hand-written defaults literal.

## 2. Runtime locale switching vs. setup-resolved catalogs

**Composing `i18n()` alone changes no text on screen, and `setLocale()` at runtime re-labels no official plugin.** This is the deliberate position of this corpus: every official plugin resolves its `messages` catalog exactly once at `setup()` from its own factory config (`sdk/dom` `resolveCatalog`; the rule is restated per plugin across the corpus — data-store.md, tree-grid.md, task-bars.md, interaction.md, undo-redo.md, a11y.md, scheduling.md, tracking.md, resource.md, export.md, portfolio.md, perf-tools.md) and never consults this dictionary afterwards. `stargantt.i18n` is the supply side: the host reads translations out of it — typically via `createDictionary` before `Gantt.create()` — and passes them into the sibling factories as their `messages` configs; only those configs move pixels. Changing the chart's language therefore means re-creating the instance with re-resolved `messages` configs; `setLocale` serves consumers that resolve through `t()` / `catalog()` live (hosts, third-party plugins that choose to subscribe to `state`).

**Deliberate non-feature.** Live re-labeling of official plugins without re-creation would require a corpus-wide obligation — every catalog-bearing plugin re-running its `resolveCatalog` merge against a subscribed dictionary and repainting its text surfaces — that this corpus does not define. If that capability is ever wanted, it is a corpus-wide amendment touching every Messages section in `docs/specs/plugins/`, not an amendment to this file alone; this document deliberately does not claim it works today.

## Extension points

None defined, none contributed.

## Commands

None.

## Events

None emitted, none subscribed. Dictionary changes are observed via `state.subscribe()` (§1.3); there is no `i18n/changed` event (the name stays out of `tools/official-events.mjs`).

## Config

Factory: `i18n(config?: I18nConfig)`. Every field optional; `i18n()` ≡ `i18n({})`; unusable values silently fall back; the config object is snapshotted once at `setup()` — later mutation of the caller's objects has no effect.

| Field | Default | Semantics |
|---|---|---|
| `locale` | `PluginContext.locale` (hostless: `"en"`) | the active locale; non-string or empty falls back |
| `fallbacks` | `["en"]` | consulted in order after the active locale (§1.2); unusable entries dropped per entry; a non-array keeps the default |
| `translations` | none | initial dictionaries, applied through the `add()` path (same per-entry drop rules); a non-object is ignored wholesale |

## Messages

None. The plugin emits no user-visible text of its own — it manages the other plugins' catalogs — so it declares no `Messages` interface and no `messages` config field.

## Dependencies

None — `dependsOn: []`, `meta.optional: []` (a translation supplier; consumed by hosts and by third parties, never consuming). Layer 8 placement is compositional only: nothing orders against this plugin. `setup()` builds the dictionary, provides the service, and owns nothing else — no DOM, no timer, no subscription. Service methods never throw on bad input; programming errors surface through the core error boundary as usual.

## Third-party surface

- **Consumable services:** `stargantt.i18n` (`I18nService`) — third-party plugins and hosts resolve their own message catalogs through the same `t()` / `catalog()` mechanism official plugins' hosts use (the shared `messages`-catalog convention), supply translations via `config.translations` / `add()`, and observe locale/dictionary changes via `state.subscribe()` (auto-disposed through `ctx.own()`).
- **Hostless form:** `createDictionary()` is public — usable before `Gantt.create()` and in tests, with the identical lookup semantics and a working `state` store.
- **Contributable extension points:** none defined.
- **Subscribable events:** none; changes are observed via the store.
- **Reserved namespaces (documentation convention only):** the `stargantt.i18n` service ID; official catalog key prefixes follow the plugin camel-name convention (`"treeGrid."`, `"scheduling."`, …), and third parties prefix their dictionary keys with their own plugin name. Not enforced in core.
